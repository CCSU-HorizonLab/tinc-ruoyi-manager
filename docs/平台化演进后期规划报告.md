# 平台化演进后期规划报告

更新日期：2026-09-15。

> 当前实施优先级：先彻底跑通和稳定现有 Tinc 全链路。本报告仅作为后期规划基线，在基础 Tinc 验收完成前不启动插件化重构。

## 一、总体判断

当前系统的 Tinc 耦合同时存在于领域模型、Java 编排、客户端协议和 Agent 运行状态机。项目不适合一次性推倒重写，应采用绞杀者模式：先在现有 Tinc 链路外建立通用平台契约，把已稳定的实现包装成第一个 `network.tinc` 插件，再逐层将核心中的 Tinc 语义迁入插件。

现有可利用的演进支点：

- 服务端已有 `TincRuntimeManager`、`TincConfigTransport` 接口。
- 客户端已分为 Vue UI、Tauri bridge、IPC、Agent、`vpn-core` 和平台适配层。
- 客户端已经具备受限 IPC、服务身份验证、原子配置 generation、进程所有权、精确路由清理等可保留的平台能力。

## 二、现状与痛点

### 2.1 服务端

1. `TincNetworkMange`、`TincNodeMange`、`MangeServer` 及对应 Mapper/表将 Tinc 当成核心领域，而不是一种网络实现。
2. `TincNetworkMangeServiceImpl` 直接编排 RSA、`tinc.conf`、host、脚本和运行时启动，业务用例与插件实现混合。
3. `TincConfigUtils` 同时承担模板、文件、远程传输、并发锁和密钥事务，并通过静态注入持有全局状态。
4. `TincRuntimeManager` 虽然是接口，方法和状态仍固定为 tincd、systemd、HUP、Interface、Port 和 Tinc 私钥语义。
5. 客户端 API 固定为 `login -> ZIP -> PKCS#1 RSA 公钥上传 -> server_master`，其他配置或凭据模型难以复用。
6. 管理端路由、API、权限字符和 Vue 页面仍以 `tinc` 命名，网段/端口表单为静态实现。
7. 监控 Controller 直接读取 Tinc domain，并混入随机生成的响应时间、健康分和流量，尚未形成可信的 Observed State。
8. 节点编辑流程曾使用 `password` 字段承载/识别 PEM 公钥，身份凭据与插件密钥职责混用。

### 2.2 客户端

1. `Identity` 固定为 `net_name/node_ip`，IPC 固定为 `StartVpn/StopVpn`。
2. HTTP Session 固定调用 `/api/tinc/client/login`、`config/download`、`key/upload`。
3. 配置模块只接受 `tinc.conf`、`hosts/*`、`ConnectTo`、`server_master` 和 `/32 Subnet`。
4. 密钥模块固定生成 RSA PKCS#1；Engine 固定检查 Tinc 1.0.x 并执行 `tincd -D -c`。
5. 网卡和健康逻辑固定围绕 TAP 地址、到 `server_master` 的 `/32` 路由及 ICMP 探测。
6. 安装配置包含 `TincClientAgent`、`tinc_binary`、TAP-Windows V9；UI 品牌、文案、按钮和流程也固定为 Tinc/VPN。

## 三、目标架构

```text
管理端 Vue / 客户端 HTML UI
              |
      Platform API + JSON Schema
              |
  调度编排 / Assignment / Task / State
              |
        Network Plugin SPI
         +-----------+
   network.tinc   network.fnps
         |             |
  受限运行执行器 / Client Agent Plugin Host
         |
 systemd、文件、TAP、路由、进程、健康探测
```

平台核心只认识 Server/Gateway、Network Instance/Fabric、Node/Endpoint、Connection Assignment、Desired State、Observed State、Operation Task 和 Plugin Descriptor/Capability。`tinc.conf`、`server_master`、RSA PKCS#1、tincd HUP 以及 fnps 专属配置只属于各自插件。

## 四、JSON 通信协议

建议新增 `/api/platform/v2`，旧 `/api/tinc/client/*` 在迁移期继续存在。

### 4.1 客户端能力声明

```json
{
  "protocolVersion": "2.0",
  "client": {
    "clientVersion": "0.2.0",
    "platform": "windows",
    "arch": "x86_64",
    "installedPlugins": [
      {
        "id": "network.tinc",
        "version": "1.0.0",
        "apiVersion": "network-plugin/v1"
      }
    ]
  },
  "credential": {
    "type": "password",
    "principal": "node-name",
    "secret": "<仅登录请求使用>"
  }
}
```

会话建立后，v2 Token 应使用 `Authorization: Bearer`，不再重复置于每个 JSON body。

### 4.2 Connection Assignment

```json
{

  "assignment": {
    "id": "asn_01",
    "revision": 7,

    "identity": {

      "addresses": [{"family": "ipv4", "address": "10.0.11.211", "prefixLength": 32}],
      "routes": [{"destination": "10.0.11.1", "prefixLength": 32, "scope": "plugin-owned"}]

      "configFormat": "tinc-1.0",
      "profileName": "new_network",
      "peerId": "server_master",

      {
        "id": "config-main",

  },
  "traceId": "trace_..."

```

fnps 插件可以提供不同的 `pluginConfig`、artifact 和 capability；核心不得假定所有插件都有虚拟地址、TAP 或 ICMP。

### 4.3 状态与错误

平台状态使用 `assignmentId/revision/pluginId/desiredState/observedState/phase/conditions/pluginStatus`。插件详情只放在受 Schema 约束的 `pluginStatus` 中。

核心错误码建议包含：

- `PLUGIN_NOT_FOUND`
- `PLUGIN_NOT_INSTALLED`
- `PLUGIN_VERSION_INCOMPATIBLE`
- `PLUGIN_CONFIG_INVALID`
- `ASSIGNMENT_STALE`
- `ASSIGNMENT_EXPIRED`
- `ARTIFACT_DIGEST_MISMATCH`
- `CAPABILITY_NOT_SUPPORTED`
- `OPERATION_CONFLICT`
- `RUNTIME_NOT_READY`
- `CREDENTIAL_EXCHANGE_FAILED`

Tinc 错误保留在 `network.tinc/*` 命名空间，避免继续扩张平台核心枚举。

### 4.4 安全边界

服务端不得通过 Assignment 下发任意 Shell、任意可执行路径、任意 JavaScript/HTML、未签名二进制或私钥。Schema 只能描述数据和受限 UI 提示。特权插件必须经过管理员安装和签名验证，普通请求只能选择客户端已经安装且声明支持的插件能力。

## 五、Java 端解耦

近期先使用 Spring Strategy Registry，而不是直接做热加载：

```java
public interface NetworkPlugin {
    PluginDescriptor descriptor();
    JsonNode configurationSchema();
    ValidationResult validate(PluginContext context, JsonNode config);
    OperationPlan plan(DesiredState desired, PluginContext context);
    ClientAssignment prepareAssignment(NodeContext node);
    RuntimeSnapshot inspect(NetworkInstance instance);
}
```

由 `PluginRegistry` 注入 `List<NetworkPlugin>` 并按 `pluginId` 建立不可变映射。现有能力逐步映射：

- `TincRuntimeManager` -> `TincPluginRuntime`
- `TincConfigUtils` -> `TincPluginConfigurator`
- `TincNetworkStatus` -> `RuntimeSnapshot + pluginStatus`
- `TincRuntimeErrorCode` -> Tinc 插件错误空间

编排分为 `NetworkOrchestrationService`、`NetworkPlugin`、`PrivilegedOperationExecutor` 三层。执行计划只能包含 `WriteArtifact`、`EnsureService`、`ReloadService`、`EnsurePort`、`InspectProcess` 等结构化动作，禁止 `execute(String command)`。

近期插件作为可信 Maven module 编译进服务端；后期再考虑 PF4J、独立 ClassLoader 或独立 Plugin Runner。涉及 root 能力的第三方插件优先放进隔离进程，不直接装入主 Spring Boot JVM。

## 六、客户端解耦

建议拆分为：

- `agent-core`
- `network-plugin-api`
- `network-plugin-tinc`
- `platform-windows`
- `platform-linux`

`NetworkDriver` 负责插件级 `validate_assignment/configure/start/stop/inspect/recover`。现有 ZIP、RSA、`server_master`、Tinc 版本检查和 tincd 进程逻辑进入 `network-plugin-tinc`；IPC 身份验证、原子文件、进程监管、网络配置和恢复保留在 core/platform。

IPC 继续只开放固定动作：`login`、`resolve_assignment`、`configure`、`start`、`stop`、`get_status`、`logout`。不能改为任意 `plugin_command`。

## 七、Schema 动态表单

插件同时提供 JSON Schema、UI Schema 和 Capability。核心 UI 只固定插件类型、服务器/节点、名称说明、Desired State 和当前状态；插件参数由白名单组件渲染，例如 text、secret、number、boolean、select、CIDR、port、endpoint 和有限的 array/object group。

前后端使用同一 `schemaId + schemaSha256`。前端校验只用于交互体验，Java 核心和插件仍必须做最终校验。Schema 不允许包含脚本、HTML 或可执行命令。

## 八、Roadmap

### Phase 0：冻结现状

- 固化 Tinc 登录、配置、启动、HUP、停止和恢复的契约测试。
- 定义 Assignment、Desired State、Observed State 和插件版本规则。
- 区分真实监控数据与模拟数据。

### Phase 1：服务端插件内核

- 新增 `NetworkPlugin`、`PluginRegistry`。
- 用 `TincNetworkPlugin` 包装现有 `TincRuntimeManager/TincConfigUtils`。
- 把创建编排迁到通用 Orchestration Service。
- 旧 Controller、数据库和页面暂时不变。

### Phase 2：v2 双协议

- 客户端声明平台、Agent 版本和已安装插件。
- 服务端返回通用 Assignment。
- Tinc Adapter 映射现有 ZIP、公钥交换和 READY 状态。
- 使用 revision、ETag、Idempotency-Key 防止旧配置覆盖和重复执行。

### Phase 3：客户端 Core/Plugin 分离

- 将 Tinc 配置、密钥、进程和探测搬入 `network-plugin-tinc`。
- IPC 状态加入 `pluginId/assignmentId/revision`。
- UI 按 capability 和状态显示操作。

### Phase 4：管理端通用化

- 使用 expand-contract 方式增加通用模型，不立即删除或重命名旧表。
- 引入通用网络页面和 Schema Renderer。
- 原 Tinc 页面在过渡期代理到通用 API。

### Phase 5：fnps 参考插件

- 只新增插件 module、Schema、执行适配和测试。
- 不修改 Agent 核心状态机、通用表单和 Assignment DTO。

### Phase 6：插件生命周期

- 插件签名、兼容矩阵、安装、升级、回滚、禁用和吊销。
- 服务端插件隔离、插件级日志和指标、灰度 Assignment。
- 最后才考虑动态热加载。

## 九、第一步

基础 Tinc 全链路验收完成后，第一处最稳妥的代码切口是：先定义通用 `Assignment` 和 `NetworkPlugin` SPI，再用 `TincNetworkPlugin` 无行为变化地包装现有实现。不要先做全局 Tinc 重命名、数据库重构或客户端重写。
